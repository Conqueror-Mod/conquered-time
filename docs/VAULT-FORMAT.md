# Conquered Time — Vault Format Spec

Shared source of truth for any non-desktop client (Android, etc.) that reads a
Conquered Time vault. The desktop implementation lives in
`src/main/vault-crypto.js` and `src/main/main.ts` (schema). **If you change the
crypto or schema on the desktop, update this file and the Android port.**

## File

A vault is a plain **SQLite database file** (`vault.db`), written by sql.js. It
uses the standard SQLite on-disk format, so any SQLite reader (including
Android's built-in `android.database.sqlite`) opens it directly. Profiles live
at `conquered-data/profiles/<username>/vault.db` on desktop; on Android the user
imports this file.

## Encryption

- **KDF:** `PBKDF2WithHmacSHA256(password, salt, 310000 iterations, 256-bit key)`.
- **Salt:** the `users.key_salt` column — a **64-character hex string**. It is
  fed to PBKDF2 as a *string*, so the salt bytes are the **64 UTF-8 (ASCII)
  bytes of that string, NOT the 32 bytes it hex-decodes to**. (Legacy fallback:
  if `key_salt` is null, the desktop uses `totp_secret` as the salt string.)
- **Cipher:** AES-256-GCM, 12-byte IV, 16-byte (128-bit) auth tag.
- **Storage:** encrypted blobs are three lowercase-hex TEXT columns:
  `*_enc` (ciphertext), `*_iv`, `*_tag`. Java/Kotlin GCM wants
  `ciphertext‖tag`, so concatenate `hex(enc) + hex(tag)` before `doFinal`.
- **Bad password** → GCM auth-tag mismatch throws. That thrown exception is the
  canonical "wrong password" signal (no separate password check is needed to
  unlock, though the desktop also stores a bcrypt `password_hash`).

Encrypted blob locations:
| Data | Table | Columns |
|---|---|---|
| Company fields (name, project, platform, navId, report_email, …) | `companies` | `data_enc/data_iv/data_tag` |
| Time-entry per-row clock detail (`rows_json` array) | `time_entries` | `rows_enc/rows_iv/rows_tag` (older rows may still be plaintext in `rows_json`) |
| User profile blob | `users` | `profile_enc/profile_iv/profile_tag` |
| SMTP password | `app_settings` | keys `email_smtp_password_enc/_iv/_tag` |

## TOTP

`users.totp_secret` is a **plaintext base32 secret** (speakeasy defaults:
HMAC-SHA1, 6 digits, 30s period, ±1 window). Because it sits in plaintext next
to the data, TOTP is **not** a real boundary for an offline vault file — the
password (key derivation) is the only cryptographic gate. Treat TOTP as optional
UX parity on mobile.

The Android port (`Totp.kt`, verified by `TotpParityTest.kt` against speakeasy
vectors) implements this. In the mobile unlock UI the code is **optional**: a
non-blank code must verify (±1 window), a blank one is skipped — so a vault
whose desktop `dev_mode` bypasses TOTP is still openable without an
authenticator app.

## Rowid discipline (gotcha #1)

sql.js does not reliably populate the `id` AUTOINCREMENT column. Every read that
needs an identity must `SELECT rowid AS rid, *` and use `rid`. Android reads
should follow the same rule for consistency with entry/company references.

## Schema (read-relevant tables)

- `users(id, username, password_hash, totp_secret, totp_verified, recovery_hash,
  key_salt, display_name, profile_enc/iv/tag, recovery_key_*, …)`
- `companies(id, user_id, data_enc, data_iv, data_tag, created_at, updated_at)`
- `time_entries(id, user_id, company_id, log_date, session_label, rows_json,
  total_mins, rows_enc/iv/tag, created_at, updated_at)`
- `task_items(id, user_id, entry_id, label, item_type, started_at, stopped_at,
  duration_secs, created_at)`
- `app_settings(key, value)` — UI prefs under `ui_*`, window prefs `win_*`.

## Parity test

`android/app/src/test/java/com/conquered/time/crypto/VaultCryptoParityTest.kt`
carries vectors generated by the real Node module. Regenerate with:

```
node -e "const vc=require('./src/main/vault-crypto.js'); \
  const k=vc.deriveKey('devpass123','<64-hex-salt>'); \
  console.log(k.toString('hex'), JSON.stringify(vc.encrypt('<plaintext>', k)))"
```

Verified 2026-07-08: Kotlin/JVM `PBKDF2WithHmacSHA256` + `AES/GCM/NoPadding`
reproduce the Node key and plaintext exactly.
